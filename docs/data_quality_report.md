# FlightInsight — отчёт о качестве исходных данных

**Источник:** Bureau of Transportation Statistics (BTS), Reporting Carrier On-Time Performance (1987–present).  
**Период:** 1 января — 31 марта 2025 года (включительно).  
**Статус:** результаты локального запуска `scripts/inspect_bts.py` на трёх скачанных официальных ZIP-архивах.  
**Важно:** проверены структура, базовая полнота и несколько инвариантов. Это не полная валидация всех 109 полей и не доказательство отсутствия всех возможных дубликатов.

## 2. Структура файлов

- Все три файла прочитаны непосредственно из ZIP без распаковки на диск.
- Во всех трёх месяцах: **109 именованных столбцов** и **одна дополнительная пустая колонка заголовка в конце**.
- Пустая техническая колонка не содержит непустых значений ни в одном проверенном месяце: её следует исключать при импорте.
- Проверка не выдала предупреждения о расхождении заголовков между месяцами.
- Диапазоны дат: январь `2025-01-01`—`2025-01-31`, февраль `2025-02-01`—`2025-02-28`, март `2025-03-01`—`2025-03-31`.

## 4. Пропуски в значениях

| Колонка | Январь | Февраль | Март |
| --- | ---: | ---: | ---: |
| `DepTime` | 15 886 | 7 091 | 6 583 |
| `ArrTime` | 16 580 | 7 541 | 7 131 |
| `DepDelay` | 15 923 | 7 139 | 6 609 |
| `ArrDelay` | 17 478 | 8 408 | 8 571 |
| Каждая из пяти причин задержки* | 441 617 | 401 782 | 484 838 |

\* `CarrierDelay`, `WeatherDelay`, `NASDelay`, `SecurityDelay`, `LateAircraftDelay`. Количество пропусков по каждому из пяти полей одинаково в рамках соответствующего месяца.

Во всех месяцах `пустой ArrDelay = число отмен + число перенаправлений`; у обычных завершённых рейсов это поле непустое и числовое. Это согласуется с отдельным учётом отмен и перенаправлений, но **не означает**, что любые другие пропуски следует заменять нулями.

Для причин задержек в каждом месяце количество непустых значений в каждом из пяти полей совпадает с количеством прибытий с задержкой ≥ 15 минут. Это соответствует ожидаемой семантике BTS; однако текущий скрипт проверял совпадение **количеств**, а не построчную эквивалентность. При ETL нужно проверить её отдельно.

## 5. Правила для дальнейшей разработки

1. Сохранить неизвестные / неприменимые числовые значения как `NULL`, не подставлять `0` автоматически.
2. Отменённые и перенаправленные рейсы учитывать отдельно от статистики обычного прибытия.
3. Для KPI доли задержанных использовать `ArrDelay >= 15`, а не просто `ArrDelay > 0`.
4. Времена в исходных данных представлены местным временем аэропорта в формате HHMM, без встроенной информации о часовом поясе. Их преобразование требует отдельной проверки (включая значения `2400`, если встретятся).
5. Для сравнения перевозчиков / аэропортов показывать число рейсов в выборке.
6. Не считать название перевозчика восстановленным по `Reporting_Airline`: для отображаемых названий нужен подтверждённый справочник.
7. Не считать источник предсказательной моделью: анализ основан на исторической статистике.

## 6. Как воспроизвести проверку

Из корня репозитория в Windows CMD или PowerShell:

```bat
python scripts\download_bts.py
python scripts\inspect_bts.py
```

Архивы `data/raw/bts_2025_01.zip`, `data/raw/bts_2025_02.zip`, `data/raw/bts_2025_03.zip` не должны попадать в Git. Для воспроизводимости источники задокументированы в `docs/data_source.md`.

**Итог этапа 2:** предоставленные результаты не обнаружили ошибок по проверяемым критериям. Нормализованная схема PostgreSQL, ETL и правила уникальности будут реализованы и протестированы в последующих этапах.
